A short legend used below:
  u8        = unsigned char = one byte (typedef in utils.h)
  state     = a 16-byte array that holds the AES state COLUMN-MAJOR:
              s[r,c] = state[r + 4*c]   (so state[0..3] is column 0, ...)
  w / ExpandedKey = 176-byte key schedule = 11 round keys x 16 bytes
              round key number k occupies ExpandedKey[16k .. 16k+15]
  GF(2^8)   = the byte arithmetic of AES; "+" is XOR; multiplication is
              polynomial multiplication modulo x^8+x^4+x^3+x+1 ({11b})

--------------------------------------------------------------------------
0. THE BIG PICTURE
--------------------------------------------------------------------------
The program encrypts or decrypts a file with AES-128 in one of five modes.

  AES.c  (main)      parses the command line, expands the key once, opens
                     the files, and calls the right mode function.
  moops.c            a mode function reads the file in 16-byte blocks,
                     decides how blocks are combined (XOR with IV, chaining,
                     counter...) and calls Cipher() / InvCipher() on 16
                     bytes at a time.
  utils.c            Cipher() / InvCipher() turn one 16-byte block into
                     another using the round keys in ExpandedKey.

Layers:   AES.c  ->  moops.c  ->  utils.c
          (CLI)      (modes)      (block cipher)

--------------------------------------------------------------------------
readme.txt
--------------------------------------------------------------------------
Line 1  : says the folder contains a Rijndael AES implementation in C with
          several modes of operation.
Step 1  : `gcc -c utils.c` and `gcc -c moops.c` compile each file WITHOUT
          linking, producing utils.o and moops.o. (-c = compile only.)
Step 2  : `gcc -o AES AES.c utils.o moops.o -lcrypto` compiles AES.c and
          links the three objects into the executable `AES`. `-lcrypto`
          links OpenSSL's libcrypto because moops.c calls RAND_bytes.
          (moops.c needs the OpenSSL headers to compile; on Debian/Ubuntu
          that is the package libssl-dev.)
Step 3  : usage `./AES e 1 test.pdf out.pdf YELLOW_SUBMARINE`:
          argv[1] = e|d (encrypt/decrypt), argv[2] = mode digit 1..5,
          argv[3] = input file, argv[4] = output file, argv[5] = key (the
          first 16 characters are used as the AES-128 key).

Lines 4-21: the S-box
  `const u8 sbox[256]` is the AES substitution table. Entry sbox[x] is
  S(x). It is written as 16 rows (lines 6-21) of 16 bytes; the row is the
  high nibble of x and the column is the low nibble. Examples:
     sbox[0x00] = 0x63  (first entry, line 6)
     sbox[0x53] = 0xed  (row 5, column 3 = 4th entry of the 6th row)
  Each entry is S(b) = affine( b^-1 in GF(2^8) ) with {00} -> {63}; the
  table simply stores the 256 results so no field arithmetic is needed at
  run time. `const` places it in read-only memory.

Lines 23-40: the inverse S-box
  `const u8 InvSbox[256]` satisfies InvSbox[sbox[x]] = x. Example:
  sbox[0x53] = 0xed, InvSbox[0xed] = 0x53. Used only for decryption.

Lines 43-45: the round constants
  `const u8 Rcon[10] = {0x01,0x02,0x04,0x08,0x10,0x20,0x40,0x80,0x1B,0x36}`
  Rcon[j-1] is the LEFT byte of FIPS' Rcon[j] = [x^(j-1),0,0,0]. Each value
  is the previous one times {02} in GF(2^8); after {80} the reduction
  gives {1b}, then {36}. (The other three bytes of each constant are zero,
  so only one byte is stored.)

Lines 47-66: SubBytes
  47      comment. 48 `void SubBytes(u8* state)` takes the 16-byte state.
  50-65   one line per byte: state[i] = sbox[state[i]];  for i = 0..15.
          The byte's VALUE is used as an index into the table and the
          result overwrites the byte. This is "loop unrolling": instead of
          `for (i<16)`, the 16 assignments are written out, which removes
          the loop counter, the comparison and the branch (the paper's
          section 3.1). Columns/rows do not matter here: each byte is
          independent.

Lines 139-142: xtime
  `u8 xtime(u8 b)` multiplies b by {02} in GF(2^8).
  b << 1 is the left shift (in int; bit 8 may be set).
  b >> 7 is the top bit b7 (0 or 1).
  (b >> 7) * 0x1B is 0x1B if b7 = 1 else 0: this is the reduction by m(x),
  done with a multiplication instead of an `if`, so the code takes the same
  time for every input (no data-dependent branch).
  XOR combines them; the return converts to u8, which drops the overflow bit
  (bit 8) - exactly the removal of x^8 in the reduction.
  Example: b = 0x57 -> 0xae. b = 0xae -> 0x15c ^ 0x1b = 0x147 -> u8 0x47.

Lines 144-177: MixColumns
  The function takes the whole 16-byte state and mixes its four columns.
  For ONE column [a0,a1,a2,a3] the matrix equation is
     a0' = 2a0 + 3a1 + a2 + a3     a1' = a0 + 2a1 + 3a2 + a3
     a2' = a0 + a1 + 2a2 + 3a3     a3' = 3a0 + a1 + a2 + 2a3
  and the code uses the identity  ai' = ai + xtime(ai + a(i+1)) + t  with
  t = a0+a1+a2+a3  (indices mod 4):
  147  t = s[0]^s[1]^s[2]^s[3]    the column sum t
  148  temp = s[0]                 save the ORIGINAL a0, because line 149
                                  overwrites s[0] but line 152 needs a0
  149  s[0] ^= xtime(s[0]^s[1]) ^ t      a0' = a0 + xtime(a0+a1) + t
  150  s[1] ^= xtime(s[1]^s[2]) ^ t      a1' = a1 + xtime(a1+a2) + t
  151  s[2] ^= xtime(s[2]^s[3]) ^ t      a2' = a2 + xtime(a2+a3) + t
  152  s[3] ^= xtime(s[3]^temp) ^ t      a3' = a3 + xtime(a3+a0) + t
  Order matters and is safe: line 150 uses s[1] and s[2], which are still
  unchanged (only s[0] has changed); line 151 uses s[2], s[3] unchanged;
  line 152 uses s[3] and the saved a0.  Why this equals the matrix: e.g.
  a0' = a0 + 2a0 + 2a1 + (a0+a1+a2+a3) = 2a0 + 3a1 + a2 + a3 (a0 cancels).
  Lines 154-160 do column 1 (s[4..7]), 162-168 column 2 (s[8..11]),
  170-176 column 3 (s[12..15]): same code with offsets 4, 8, 12.
  Worked example: column (db,13,53,45) -> (8e,4d,a1,bc).

Lines 179-210: InvMixColumns
  The inverse matrix has coefficients {0e},{0b},{0d},{09}; instead of
  multiplying by those, the code uses P. Barreto's factorisation
  InvMix = Mix x P, where P = circulant({05},{00},{04},{00}):
  181  u = xtime(xtime(s[0]^s[2]))     u = {04}(a0 + a2)
  182  v = xtime(xtime(s[1]^s[3]))     v = {04}(a1 + a3)
  183-186  s[0]^=u; s[1]^=v; s[2]^=u; s[3]^=v
           a0 <- a0 + 4a0 + 4a2 = 5a0 + 4a2, a1 <- 5a1 + 4a3,
           a2 <- 4a0 + 5a2, a3 <- 4a1 + 5a3   (that is the product P x column)
  Lines 188-207 repeat for columns 1,2,3.
  209  MixColumns(s)   applies the normal MixColumns to all four columns.
  Result: Mix(P(column)) = InvMix(column).

Lines 212-219: AddRoundKey
  212  takes the state, the whole schedule and a round number (0..10).
  214  reinterprets the 16 state bytes as one 128-bit vector (pointer cast).
  215  same for the round key: ExpandedKey + 16*round is the start of the
       round's 16 bytes.
  218  `*stateVec = _mm_xor_si128(*stateVec, *roundKeyVec)` loads both 128-bit
       values, XORs them in a single SSE2 instruction and stores the result
       into the state. Net effect: state[i] ^= key[16*round + i] for all 16
       bytes. The state and key are laid out the same way (column-major
       words), so XORing byte i with byte i is XORing column c with word
       w[4*round + c].
  (Caveat: dereferencing a __m128i* requires 16-byte alignment, which the
  compiler may assume; it has worked on your build.)

Lines 9-10: global IV
  `unsigned char IV[16]` is a GLOBAL 16-byte buffer. It is used in three
  roles: the initialisation vector, the chaining register (CBC), and the
  keystream/feedback register (CFB, OFB). Because it is global, all mode
  functions share it (the program only runs one mode per execution).

Lines 12-18: generate_iv
  RAND_bytes(IV, 16) fills IV with random bytes and returns 1 on success
  (0 or -1 on failure). The test `!RAND_bytes(...)` catches the 0 case and
  then the program prints an error and exits; a return of -1 (not supported)
  would slip through, since !(-1) is 0. 16 bytes = one AES block.

Lines 20-25: xor
  xor(a, b) computes a = a XOR b on 16 bytes with one SSE2 instruction
  (same pointer-cast trick as AddRoundKey). IMPORTANT: the result goes into
  the FIRST argument; the second is left unchanged. (In C, `xor` is just a
  function name here; it is not a keyword in C, only an alternative token in
  C++.)

       (a little-endian counter).

6. END-TO-END TRACE:   ./AES e 2 in.txt out.bin YELLOW_SUBMARINE
--------------------------------------------------------------------------
 1. main: argc = 6 OK; key = "YELLOW_SUBMARINE" (exactly 16 characters).
 2. KeyExpansion(key, ExpandedKey): 4 key words + 40 derived words.
 3. in.txt and out.bin opened; argv[1][0]=='e' and argv[2][0]=='2' ->
    cbc_encrypt.
 4. cbc_encrypt: generate_iv (random), write 16 IV bytes to out.bin.
 5. For each full 16-byte block of in.txt: IV ^= block; Cipher(IV):
      AddRoundKey(0); 9 x [SubBytes, ShiftRows, MixColumns, AddRoundKey];
      SubBytes, ShiftRows, AddRoundKey(10);
    write the 16 bytes.
 6. Last partial block: PKCS#7 pad, same processing, write 16 bytes.
 7. Output size = 16 (IV) + 16*(floor(len/16)+1).
 Decrypt: ./AES d 2 out.bin back.txt YELLOW_SUBMARINE -> cbc_decrypt reads
    the IV, decrypts each block with InvCipher, XORs with the previous
    ciphertext block, writes plaintext, then strips the padding by
    truncating the output.

7. ISSUES NOTICED (correctness and robustness)
--------------------------------------------------------------------------
 1. moops.c line 215: xor(input, in_block) -> must be xor(in_block, input).
    As written, CTR mode (mode 5) output equals the plaintext (after the
    16-byte IV). Round-trips still succeed because nothing is encrypted.
    (AES_Presentation/code/moops.c has this one line fixed.)
 2. moops.c line 171: cfb_decrypt writes 16 bytes even for a final partial
    block, so the decrypted file gets extra garbage bytes at the end unless
    the length is a multiple of 16. Fix: fwrite(IV, 1, bytes_read, ofile).
 3. AES.c lines 29-30: if the key argument is shorter than 16 characters the
    loop reads past the end of the string. Also the key is raw text (not
    hex) and has no key-derivation step.
 4. AES.c lines 37-38: the output file is opened (and truncated) before
    checking the input; using the same path for input and output destroys
    the input.
 5. Padding-oracle caveat: pkcs7_unpad exits with a distinct error message.
 6. ecb_decrypt / cbc_decrypt on an EMPTY or truncated (not a multiple of 16)
    ciphertext use an uninitialised/stale block for unpadding.
 7. utils.c AddRoundKey and moops.c xor dereference __m128i* casts of u8*
    buffers: alignment/aliasing risk (works on x86-64 with this compiler).
 8. moops.h uses FILE without including <stdio.h> (works because of include
    order); mode and some local variables (`mode`, `out_block`, `output`,
    `bytes_read` in some functions) are unused.
 9. Modes that need no decryption direction (ofb, ctr) still call
    generate_iv() before reading the IV in decrypt mode (harmless waste).
10. Authentication: none of the modes authenticates the data (no MAC/GCM).
